# SonarQube Cloud setup

[Português](sonarqube-cloud.pt-BR.md) | **English**

ReliableWebhooks includes optional SonarQube Cloud analysis in `.github/workflows/sonar.yml`. The workflow is disabled until the repository secret `SONAR_TOKEN` is configured.

## What the workflow does

When enabled, the workflow runs on pull requests targeting `main` and on pushes to `main`. It restores the pinned SonarScanner for .NET, restores NuGet dependencies in locked mode, performs a non-incremental Release build, runs tests with OpenCover output, imports coverage, reports the project version, and waits for the Sonar Quality Gate.

The primary CI workflow remains responsible for the normal build, warnings-as-errors policy, tests, package validation, and CI artifacts. SonarQube Cloud complements that baseline rather than replacing it.

## Configure the SonarQube Cloud project

Create or import the ReliableWebhooks project in SonarQube Cloud and bind it to this GitHub repository. The workflow derives conventional defaults from the GitHub repository:

```text
project key  = <github-owner>_<repository-name>
organization = <github-owner>
host         = https://sonarcloud.io
```

If the Sonar project uses different coordinates, configure these GitHub Repository Variables:

```text
SONAR_PROJECT_KEY
SONAR_ORGANIZATION
SONAR_HOST_URL
```

## Configure the secret

Create the following GitHub Actions repository secret:

```text
SONAR_TOKEN=<token authorized to analyze the SonarQube Cloud project>
```

Never commit the token. If it is absent or empty, the Sonar workflow intentionally completes without starting an analysis.

## Automatic Analysis

Keep SonarQube Cloud **Automatic Analysis disabled** while this workflow is enabled. CI-based analysis is responsible for the build and coverage import, and running both modes can create duplicate or inconsistent analyses.

## Project version and New Code

The workflow reports `sonar.projectVersion` using the highest reachable SemVer release tag. Before the first release tag exists, it falls back to the MSBuild `PackageVersion`.

For the v0.1.0 development line, the fallback is therefore `0.1.0` until an actual release tag becomes reachable from `main`.

The **Previous Version** New Code strategy works well with this release model.

## Quality Gate

The workflow uses:

```text
sonar.qualitygate.wait=true
sonar.qualitygate.timeout=300
```

When analysis runs, a failed Quality Gate fails the GitHub Actions job. Fix the quality issue or intentionally adjust the project policy; do not disable the gate merely to make CI green.

## Coverage

Tests produce OpenCover output with Coverlet MTP and Sonar imports:

```text
sonar.cs.opencover.reportsPaths=**/coverage.opencover*.xml
```

The Cobertura artifact generated by the primary CI workflow is independent from the Sonar report.

## Fork pull requests

GitHub does not expose repository secrets such as `SONAR_TOKEN` to workflows triggered from forks. In that case, the workflow follows its disabled path and a successful Sonar job does not mean that Sonar analyzed the contribution.

Do not switch naively to `pull_request_target` while checking out or executing untrusted fork code with repository secrets.

## Troubleshooting

### SonarQube Cloud is reported as disabled

Confirm `SONAR_TOKEN` exists under **Settings → Secrets and variables → Actions → Secrets** and is available to the workflow event.

### Project coordinates cannot be resolved

Verify the Sonar project key and organization. Configure `SONAR_PROJECT_KEY` and `SONAR_ORGANIZATION` when the GitHub-derived defaults do not match the Sonar project.

### Quality Gate fails

Open the SonarQube Cloud project and inspect the failed conditions. A `QUALITY GATE STATUS: FAILED` result means the integration ran successfully and the project did not satisfy the configured gate.

### Coverage is missing

Confirm the test step generated `coverage.opencover*.xml` and that the scanner log reports importing it.

### Project version does not advance

Confirm releases create valid SemVer tags matching `v*.*.*`, that those tags are reachable from `main`, and that the Sonar checkout keeps `fetch-depth: 0`.

## Security

- keep `SONAR_TOKEN` only in GitHub Secrets;
- use Repository Variables for non-secret coordinates;
- do not print credentials in workflow diagnostics;
- do not execute untrusted fork code in privileged workflows;
- keep workflow repository permissions read-only unless an explicit feature requires more.
